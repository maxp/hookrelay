# 05: Webhook ingestion happy path — chat scope

**What to build:** A signed Telegram update for a known chat flows end to end: route resolution, verification, chat-scope conversion, and atomic acceptance into the durable delivery structures — deduplicated on repeat. Accepted and duplicate requests return the same empty platform success only after Valkey commits.

**Blocked by:** 03 (admin endpoint API — endpoints and the adapter core must exist).

**Status:** done

- [x] `POST /webhook/{webhook_type}/{webhook_identifier}`: type/identifier pattern validation (encoded slash, colon, whitespace, Unicode, dot segments, empty rejected); POST-only with `405` + `Allow: POST`; identical bounded `404` for unknown type, unknown identifier, identifier under another type, and disabled endpoints; UUIDv7 `X-Request-Id` on every response
- [x] Body handling: 256 KiB hard limit with declared `Content-Length` precheck and streaming enforcement (read at most limit + one byte); SHA-256 computed during the read; exact bytes not retained; `application/json` with optional UTF-8 charset parsed as media type, others `415`
- [x] Telegram Verifier: exactly one `X-Telegram-Bot-Api-Secret-Token` header compared in constant time against the stored credential; bounded failure reasons `credential_missing`, `credential_repeated`, `credential_mismatch`, `source_ip_denied`; optional operator-configured Telegram source CIDR allowlist as defense-in-depth; `403` on failure
- [x] Converter chat-scope rows of the event-to-Recipient table (message, edited_message, channel_post, edited_channel_post, business and guest message variants, deleted_business_messages, my_chat_member, chat_member, chat_join_request, chat_boost, removed_chat_boost, message_reaction, message_reaction_count, callback_query with message, stopped_message_generation); integer-aware decoding (`UseNumber`, no float64, int64 bounds, negative chat ids, canonical decimal without leading zeros); compact payload re-encoding preserving unknown fields
- [x] `accept_v1` atomic acceptance: dedup record + TTL + age index, message blob, queue RPUSH, head-state creation on first message, ready-index membership with fresh fairness sequence, stats counter — all or nothing; the candidate `message_id` is discarded on duplicate
- [x] Duplicate with identical bytes → same empty `200`, no second blob or queue entry; same Deduplication Identity with different bytes → still a duplicate, `dedup_conflicts_total` incremented with a safe structured log
- [x] Platform responses: empty `200` for accepted and duplicate; `503` + `Retry-After: 1` when Valkey cannot atomically accept; success returned only after acceptance or proven duplicate
- [x] Feature events `webhook_accepted` / `webhook_duplicate` with contract fields (`platform_event_type`, status, `duration_ms`, body/payload sizes) and ingestion metrics with bounded labels
- [x] Integration tests: fixture → stored message/queue/head-state/dedup/ready asserted at the storage seam; duplicate → no new state; Valkey unavailable → `503` with no partial state

## Comments

- 2026-09-28: Implemented. New `internal/model` (Recipient Identity + serialization, Canonical Message codec with explicit `Encode`, absent-not-null optionals); `internal/ingestion` pipeline (`handler.go`: escaped-path route validation, 405, uniform 404 incl. disabled/unknown type, source-IP resolution with trusted proxies, media type + `Content-Encoding` 415, declared and streamed 256 KiB limit with SHA-256 during the read, verifier with declared headers only, converter, `accept_v1`, response mapping, feature events, metrics) and the Telegram adapter (`telegram.go`); `accept_v1.lua` with argument and key-identity validation, marker → dedup → key types → capacity order, and all writes after every precondition; `valkey.NewMessageAcceptor` / `valkey.NewEndpointLookup` implement the ingestion ports. The app routes `/webhook/` to ingestion ahead of the public mux so path cleaning never redirects webhook routes; acceptance follows readiness when ingestion is wired.
- Scope decision: the converter implements the complete event-to-Recipient table (user, bot, relay rows, routing issues, `update_id` fallback key, event-time fields), because a chat-only converter would misclassify other updates into wrong queues. Unit tests pin the chat rows and the key non-chat rules; ticket 07 keeps the exhaustive per-row signed HTTP fixtures, the unknown-event-type metric aggregation, and the event-time warning metric (the structured warning `event_time_invalid` is already emitted). `hookrelay_routing_issues_total` is already counted on acceptance.
- Deferred to 06 as listed there: in-flight semaphore, 10 s request deadline, capacity-driven `accepting-webhooks`, and the `hookrelay_dedup_records` / `hookrelay_dedup_record_capacity` gauges. Metric outcome allowlist gained `method_not_allowed` and `unsupported_media_type` (documented in platform.md).
- Uncertain `accept_v1` outcomes (transport error after dispatch) map to `503` + `Retry-After: 1`: the platform's retry is proven duplicate if the first attempt committed.
- Tests: model codec; Telegram converter/verifier/source-IP units; handler matrix with fakes; `accept_v1` storage seam (every tuple, every key, snapshot-equal state on every refusal, argument rejection); composed-app integration over real Valkey (DB 3) for accept, duplicate, conflict, second message behind head, and Valkey-unavailable with no partial state. Live-verified with `hookrelay serve` + `hookrelay admin webhook create` + curl.
- 2026-09-28: Review follow-up. `accept_v1` counted every `hr1:dedup_age` member toward the cap while nothing removed members of TTL-expired records, which would have turned into a permanent `dedup_capacity` 503 after `max_dedup_records` acceptances; it now counts only live members (`ZCOUNT` within the retention window) and prunes up to 100 expired members after each acceptance. An empty queue with an existing head state now returns `state_inconsistent` instead of silently overwriting a possibly leased state. `wrong_type`/`state_inconsistent` and a corrupt endpoint key map to a new `internal_failure` acceptance result (`500`). Converter: chat id `0` is invalid; a known event field that is not an object is relay-scoped with `unknown_event_structure`. Ingestion takes a `gen.Clock` (no direct `time.Now`), logs truncate sender-chosen event names to 64 bytes, and the outcome mapping moved out of the acceptance path. The spec's `accept_v1` contract was amended accordingly. Kept as specified: the block marker is checked before deduplication (a retried duplicate for a blocked Recipient receives `503` until the block is cleared).
