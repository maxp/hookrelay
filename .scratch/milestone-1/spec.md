# Milestone 1 — happy-path vertical slice

Status: ready-for-agent

Specification source of truth: `CONTEXT.md`, `docs/design/*`, `docs/adr/*`. This spec fixes the Milestone 1 storage encodings, Lua script contracts, startup reconciliation contract, and the M1 subsets of the HTTP APIs, per the storage contract boundary and implementation milestones. Domain vocabulary follows `CONTEXT.md`.

## Problem Statement

An operator running a Telegram bot has no way to receive Telegram webhooks, turn them into durable, deduplicated, per-recipient ordered messages, and hand them to their processing program through a stable API. Every bot integration today must reimplement webhook verification, duplicate suppression, queueing, ordering, and failure handling. There is no hookrelay implementation at all: the design is complete, the code does not exist.

## Solution

Build the first end-to-end vertical slice of hookrelay: a Go application with an admin API and CLI to create a Telegram Webhook Endpoint, a webhook ingestion route that verifies signed Telegram updates and converts them into Canonical Messages in all four Recipient scopes, atomic Valkey-backed deduplication and per-recipient ordered queueing, a long-polling Consumer API that can claim (`wait_ms=0` through `wait_ms=30000`) and acknowledge messages with idempotent Delivery Token semantics, a bounded administrative audit Stream, structured logs and Prometheus metrics describing the flow, health/readiness endpoints gated by startup reconciliation, and a Compose stack plus CI that smoke-test the whole path automatically.

Milestone 1 is an internal tracer-bullet checkpoint, not a production-ready release. Lease expiry, negative acknowledgement, retry, dead-letter, maintenance loops, and the deployable failure path are Milestone 2.

## User Stories

1. As an operator, I want to create a Telegram Webhook Endpoint through the Admin CLI with a credential, so that Telegram can deliver signed updates to hookrelay.
2. As an operator, I want the CLI to generate a `wh_<base64url-128-bit-random>` identifier before sending the create request, so that I have a known identifier to reconcile with after a lost response.
3. As an operator, I want to create an endpoint through the raw Admin API with an optional identifier, so that automation can let the server generate the identifier when it prefers.
4. As an operator, I want endpoint creation to return `201` with a `Location`, an entity `ETag`, and safe metadata without the credential value, so that I can confirm what was created without exposing secrets.
5. As an operator, I want a conflicting Webhook Identifier to return `409`, so that accidental identifier reuse is rejected instead of silently overwriting a credential.
6. As an operator, I want creation to fail with `409 bot_endpoint_limit_exceeded` when a Bot Identity already has 100 endpoints, so that one bot cannot grow unbounded configuration.
7. As an operator, I want endpoint reads to expose only credential kind and configured state, so that credential values never leak through reads, logs, or CLI output.
8. As an operator, I want every administrative mutation to require Admin Bearer authentication and to be refused with the same `401` whether the secret is missing or wrong, so that endpoint administration is not guessable.
9. As an operator, I want Webhook Endpoint creation to be recorded in the Valkey audit Stream in the same atomic operation as the state change, so that a confirmed success proves both happened.
10. As an operator, I want critical administrative mutations to report success only after state and audit writes both succeed, so that I never trust an unaudited change.
11. As an operator, I want the Admin Secret generation check to invalidate nothing in Milestone 1 sessions (there are none), so that the M1 auth surface stays minimal and auditable.
12. As an operator, I want `hookrelay generate consumer-secret|admin-secret|webhook-id`, `hookrelay version`, and `hookrelay healthcheck`, so that I can provision secrets, identify builds, and keep a distroless container healthy without a shell.
13. As an operator, I want invalid or contradictory configuration to abort startup with exit code 2, so that a misconfigured deployment never half-starts.
14. As an operator, I want the stack to survive a restart without losing its Valkey volume and come back ready with the endpoint still present and deduplication still effective, so that redeployments are safe.
15. As Telegram, I want to POST an update to `/webhook/telegram/<webhook_identifier>` and receive an empty `200` only after hookrelay durably accepted or proved duplicate, so that redelivery stops at the right time.
16. As Telegram, I want missing, repeated, or incorrect `X-Telegram-Bot-Api-Secret-Token` to receive `403` with constant-time comparison, so that forged updates are refused without timing oracles.
17. As Telegram, I want an unknown or disabled endpoint to receive the same `404` regardless of which part was unknown, so that endpoint registration is not disclosed.
18. As Telegram, I want oversized bodies rejected with `413` and invalid JSON with `400`, so that malformed traffic never becomes a message.
19. As a bot owner, I want chat-scoped events routed by the event's `chat.id` and user-fallback events routed by their documented actor/user id, so that each conversation keeps its own ordered queue.
20. As a bot owner, I want `poll` delivered to the bot scope and unmappable-but-valid JSON delivered to the relay scope with a bounded `routing_issue.code`, so that nothing verified and valid is ever dropped.
21. As a bot owner, I want a verified known chat event with a missing or invalid chat identifier preserved as relay scope with the matching bounded routing issue, so that I can diagnose bad payloads from the message itself.
22. As a bot owner, I want the same Telegram `update_id` accepted exactly once even if it arrives on old and new endpoints during credential replacement, so that replacement windows do not duplicate messages.
23. As a bot owner, I want a repeated update with identical bytes to be a normal duplicate with the same empty `200`, so that Telegram retries are harmless.
24. As a bot owner, I want a repeated Deduplication Identity with different bytes to stay a duplicate and increment a conflict metric, so that conflicting redelivery is observable, not re-enqueued.
25. As a consumer developer, I want to claim the next message with `wait_ms=0` and receive the full Canonical Message plus a Delivery Token and lease deadline, so that my worker can process exactly one message per recipient at a time.
26. As a consumer developer, I want to long-poll with `wait_ms` up to 30,000 and receive `204` when nothing is ready, so that I do not have to spin.
27. As a consumer developer, I want `ack` to remove the message and to return the same recorded success when repeated with the same token, so that lost responses never cause double processing.
28. As a consumer developer, I want repeating a claim `operation_id` to return the recorded result while the attempt is active, `409 claim_no_longer_active` after it ended, and `409 operation_conflict` for changed arguments, so that claim replay is safe and unambiguous.
29. As a consumer developer, I want Delivery Tokens only in request bodies, never in URLs or logs, and a stale/expired/unknown token to return bounded errors, so that token handling is safe by construction.
30. As a consumer developer, I want Consumer API requests authenticated by one shared secret as a Bearer token with a uniform `401`, so that all instances of my worker pool share one authorization scope.
31. As a consumer developer, I want strict JSON body validation (16 KiB limit, depth 40, unknown fields rejected, UUIDv7 and integer typing enforced) and bounded error envelopes, so that client bugs surface as precise bounded errors.
32. As an on-call engineer, I want `/health/live`, `/health/ready`, and `/health/accepting-webhooks` on the administrative listener, so that probes can distinguish process liveness, safe serving, and ingestion acceptance.
33. As an on-call engineer, I want hookrelay to refuse readiness until startup reconciliation has validated or safely repaired the structures Milestone 1 implements, so that a damaged Valkey never silently serves.
34. As an on-call engineer, I want an ambiguity isolated to one Recipient to become a persistent block marker that blocks that recipient only, with webhook requests for it receiving a retryable `503`, so that one bad recipient cannot take down the service.
35. As an on-call engineer, I want a due lease entry (`hr1:leases` score at or before Valkey time) to hold readiness false and leave state unchanged, so that Milestone 1 never invents temporary expiry semantics.
36. As an on-call engineer, I want Prometheus metrics for accepted/duplicate webhooks, claims, acknowledgements, active leases, queue depth, ready/blocked recipients, dedup capacity, and Valkey operations, so that the flow is observable.
37. As an on-call engineer, I want structured JSON logs with the bounded envelope (`timestamp_ms`, `level`, `service`, `version`, `event`, `message`), `request_id`/`message_id`/`operation_id` correlation, and no secrets, tokens, or payloads, so that incidents are diagnosable without leaking credentials.
38. As an on-call engineer, I want `hookrelay_accepting_webhooks` to drop to `0` and `/health/accepting-webhooks` to return `503` when global or per-recipient queue capacity or dedup capacity is exhausted, while draining stays available, so that overload is explicit and recoverable.
39. As a maintainer, I want one Go module with the agreed feature-module seams and embedded versioned Lua scripts, so that later milestones extend storage without redesigning it.
40. As a maintainer, I want every Lua transition's status tuples, preconditions, affected keys, and invariants covered by integration tests against a real pinned Valkey, so that storage behavior is pinned before consumers depend on it.
41. As a maintainer, I want a Compose stack and a CI job that runs the full smoke automatically, so that the vertical slice stays working as code evolves.

## Implementation Decisions

### Scope and sequence

- A short blocker-aware `valkey-go` spike precedes the application scaffold. It verifies script load, `EVALSHA`/`NOSCRIPT` fallback, `TIME` in scripts, authentication, TLS, reconnect, timeout, OOM, script-error, and connection/multiplexing behavior against a pinned Valkey, and demonstrates the accepted client resource limits. `go-redis` is the fallback only on a demonstrated concrete blocker.
- At scaffold time the then-current stable Go release and an exact Valkey version are pinned consistently across development, Compose, CI, and build images.
- The first production Bot Platform is Telegram. The shared model and storage support `chat`, `user`, `bot`, and `relay` Recipient scopes from the first implementation; the end-to-end fixture exercises chat scope, and adapter tests cover all scope classifications Telegram can produce.

### Modules and interfaces

- One executable from `cmd/hookrelay` with command families `serve`, `admin`, `generate`, `version`, `healthcheck`. Feature packages: `app` (composition root, lifecycle, listeners, readiness), `config`, `model`, `ingestion`, `delivery`, `administration`, `valkey`, `observability`.
- `ingestion` owns route resolution, Webhook Type registry, Verifier, Converter, ResponseMapper, request acceptance policy, and the Telegram adapter. It declares a `MessageAcceptor` interface returning bounded results: accepted, duplicate, recipient-blocked, recipient-capacity, global-capacity, dedup-capacity, dependency-unavailable, internal-failure.
- `delivery` owns the claim/acknowledge use cases and declares the narrow storage interface it needs; Consumer HTTP transport stays local to it.
- `administration` owns Admin Bearer authentication, the Webhook Endpoint create/get use cases, and audit intent; administrative HTTP transport stays local to it.
- `valkey` is the only module that knows `hr1:` keys, Valkey commands, and embedded Lua scripts (`.lua` files, `//go:embed`, versioned filenames such as `accept_v1.lua`). Each script name is registered with a contract version and the body's SHA-256 digest; startup loads scripts before readiness; normal calls use `EVALSHA` with one `EVAL` retry on `NOSCRIPT` of the same embedded body; an ambiguous transport error is never retried blindly.
- `model` holds Canonical Message, Bot Identity, Recipient Identity, Message Identifier, and bounded result/error classifications. The Canonical Message JSON contract is implemented through an explicit codec (snake_case, integer `*_ms`, absent optional fields omitted, never `null`).
- Feature logic receives injectable `Clock` (process timestamps) and generator interfaces (UUIDv7, crypto-random tokens). Production randomness uses `crypto/rand`; failure aborts the operation. Leases and all deadline comparisons use authoritative Valkey `TIME` inside scripts.
- Dependencies: standard `net/http` with `http.ServeMux`, `github.com/valkey-io/valkey-go` (pending the spike), `github.com/google/uuid` for UUIDv7, `github.com/prometheus/client_golang` with private registries, `log/slog` JSON with centralized `timestamp_ms`/`message` attribute handling.

### Valkey record encodings (M1 keys)

Hash fields are strings; IDs and enums use canonical string form; integer timestamps and counters are base-10 decimals; booleans are `"0"`/`"1"`. JSON blobs use the public snake_case/integer-millisecond contract.

- `hr1:wh:<webhook_type>:<webhook_identifier>` Hash: `bot_id`, `enabled`, `credential_kind`, `credential_value` (plaintext, 1–8192 bytes), `generation_id` (UUIDv7), `created_ms`, `updated_ms`, `config_version` (starts `1`). Bot Platform is derived from the Webhook Type mapping, not stored.
- `hr1:bot:<bot_platform>:<bot_id>:webhooks` SET of `<webhook_type>:<webhook_identifier>`; hard cap 100 members per Bot Identity.
- `hr1:webhooks` ZSET, score `created_ms`, member `<webhook_type>:<webhook_identifier>`.
- `hr1:audit` Stream; entry fields: `event_id` (UUIDv7), `timestamp_ms`, `actor` (`admin_bearer` in M1), `operation` (bounded, e.g. `webhook_endpoint_created`), `target` (`<webhook_type>:<webhook_identifier>`), `request_id`, `outcome`, optional bounded `reason`. Appended with `MAXLEN ~ 1000000`; 30-day trimming arrives with maintenance.
- `hr1:d:<dedup_identity_digest>` Hash: `message_id`, `body_digest`, `accepted_ms`, `expires_ms`; TTL = dedup retention. The digest is lowercase-hex SHA-256 over `webhook_type \n bot_platform \n bot_id \n platform_deduplication_key` (components contain no control characters; Telegram keys are decimal `update_id` or `body_sha256_v1:<base64url>`). `body_digest` is lowercase-hex SHA-256 of the exact request body.
- `hr1:dedup_age` ZSET, score `accepted_ms`, member `dedup_identity_digest`.
- `hr1:m:<message_id>` one compact JSON blob — the Canonical Message envelope exactly per the message contract (`message_id`, `received_ms`, optional `occurred_ms`, `recipient` object, optional `source_event_id`, `platform_event_type`, `payload`, optional `routing_issue`). No TTL in M1; deleted at acknowledgement.
- `hr1:r:<recipient_identity>:q` List of `message_id` values, head at index 0. Recipient serialization: `<bot_platform>:<bot_id>:(chat:<chat_id>|user:<user_id>|bot|relay)`.
- `hr1:r:<recipient_identity>:s` Hash: `status` (`ready`|`leased` in M1), `head_message_id`, `delivery_cycle` (starts `1`), `attempt` (starts `1`), `delivery_token` (plaintext, only while leased), `claimed_ms`, `lease_expires_ms` (only while leased), `consumer_instance_id` (optional). Invariant: `state.head_message_id == LINDEX(queue, 0)`; a non-empty queue always has a state; the state is deleted with the queue when the last message is acknowledged.
- `hr1:ready` ZSET, member `recipient_identity`, score = fairness sequence from `hr1:ready_seq` (`INCR` per allocation). At most one member per recipient.
- `hr1:leases` ZSET, member `recipient_identity`, score `lease_expires_ms`; a member exists only while head state is `leased`. `hr1:retries` is reserved for Milestone 2 and untouched in M1.
- `hr1:op:<operation_id>` claim operation record, TTL 10 minutes (fixed). Fields: `kind` (`claim`), `args_digest` (over `operation_id` + `wait_ms`), `state` (`empty` | `active` | `no_longer_active`), and for `active`: `delivery_token`, `message_id`, `recipient_identity`, `delivery_cycle`, `attempt`, `claimed_ms`, `lease_expires_ms`. The recorded response is replayed by re-reading `hr1:m:<message_id>`; the plaintext token lives only here and in head state.
- `hr1:t:<delivery_token_digest>` (SHA-256 hex of the full token) — one key with two phases. Active phase (created by claim, TTL 10 minutes + remaining lease): `state=active`, `recipient_identity`, `message_id`, `operation_id`, `claimed_ms`, `lease_expires_ms`; this is the token→attempt index that lets `ack` locate the attempt. Terminal phase (written by ack): `state=acknowledged`, `message_id`, `acknowledged_ms`, TTL 1 hour (fixed). Ack deletes plaintext token copies from `hr1:t` active phase, head state, and rewrites the claim op record to `state=no_longer_active` (so claim replay returns `claim_no_longer_active` until its TTL expires). `nack`/expiry phases arrive in Milestone 2.
- `hr1:success:<message_id>` Hash, TTL 24 hours (fixed): `recipient_scope`, `bot_platform`, `received_ms`, `acknowledged_ms`, `delivery_cycle`, `attempt_count` (`= attempt`), `consumer_instance_id` (optional). Never contains Bot/Chat/User identifiers, tokens, or payload.
- `hr1:q:<recipient_identity>` block marker Hash: `detected_ms`, `reason_code` (bounded M1 allowlist: `queue_head_mismatch`, `head_message_missing`, `head_state_missing`, `unsupported_key_type`).
- `hr1:blocked` ZSET, score `detected_ms`, member `recipient_identity`; always consistent with existing markers.
- `hr1:a:<message_id>` attempt history List: contract fixed now (compact JSON entries, `kind="attempt"`, safe metadata only: `delivery_cycle`, `attempt`, `claimed_ms`, `lease_expires_ms`, `completed_ms`, `outcome`, bounded `reason_code`, optional `consumer_instance_id`); entries are appended by Milestone 2 nack/expiry transitions. M1 writes no entries; the ack transition deletes any existing history (M1 finds none).
- `hr1:stats:queued_messages` derived global counter, `INCR`/`DECR` inside accept/ack scripts only; repaired by reconciliation.

### Lua script contracts (v1)

All scripts validate arguments, key types, and preconditions before the first write; obtain authoritative time via `TIME`; return a RESP array whose first element is a bounded status code followed by documented positional fields; a typed Go parser rejects unknown statuses and shapes. Because a runtime error does not roll back earlier writes, scripts order writes so that partial failure leaves detectable (never silently wrong) state, and no caller retries an uncertain script blindly.

- **`endpoint_create_v1`** — KEYS: endpoint Hash, Bot Identity SET, global listing ZSET, audit Stream. ARGV: `webhook_type`, `webhook_identifier`, `bot_platform`, `bot_id`, `enabled`, `credential_kind`, `credential_value`, `generation_id`, `event_id`, `operation`, `request_id`. Preconditions: endpoint key absent (`conflict`), `SCARD` bot SET < 100 (`bot_endpoint_limit`), expected key types. Writes: HSET endpoint (created/updated from `TIME`, `config_version=1`), SADD, ZADD, XADD audit. Returns: `created` + `created_ms`, `updated_ms` | `conflict` | `bot_endpoint_limit` | `wrong_type`.
- **`accept_v1`** — KEYS: dedup Hash, `dedup_age`, message blob, queue, head state, `ready`, `ready_seq`, `leases`, `blocked` index, block marker, stats counter. ARGV: `message_id`, `dedup_identity_digest`, `body_digest`, `received_ms`, `occurred_ms` (empty when absent), `message_json`, `recipient_identity`, `max_queued_messages_global`, `max_queued_messages_per_recipient`, `max_dedup_records`, `dedup_retention_ms`. Preconditions in order: marker absent (`recipient_blocked`); dedup record absent (`duplicate` + original `message_id`; `duplicate_conflict` + original `message_id` when stored `body_digest` differs — still a duplicate, never re-enqueued); expected key types (`wrong_type`; checked before the capacity reads because `LLEN`/`GET`/`ZCOUNT` on an unexpected type would raise a runtime error); an empty queue has no head state (`state_inconsistent`, never overwritten); `LLEN+1` ≤ per-recipient limit (`recipient_capacity`); counter < global limit (`global_capacity`); live `dedup_age` members (score within the retention window, `ZCOUNT`) < max records (`dedup_capacity`). Writes: dedup record + PEXPIREAT + ZADD `dedup_age`; SET message blob; RPUSH queue; on first message in queue: HSET state `{status=ready, head_message_id, delivery_cycle=1, attempt=1}` and ZADD `ready` with `INCR ready_seq`; INCR stats counter; then ZREM at most 100 `dedup_age` members whose score is older than the retention window (their records already expired by TTL), so the index cannot grow without bound between reconciliations. A recipient with a leased head accepts new messages normally (they queue behind). Capacity failures create nothing (no dedup record, no blob, no queue append). Returns: `accepted` + `accepted_ms` | `duplicate`/`duplicate_conflict` + original `message_id` | `recipient_blocked` | `recipient_capacity` | `global_capacity` | `dedup_capacity` | `wrong_type` | `state_inconsistent`. `wrong_type` and `state_inconsistent` map to the internal-failure acceptance result (`500`), not a retryable dependency failure.
- **`claim_v1`** — KEYS: `ready`, `leases`, `blocked`. ARGV: `operation_id`, `args_digest`, `max_active_leases`, `claim_op_ttl_ms`, `initial_lease_duration_ms`, `delivery_token` (app-generated `dlv_<base64url-128-bit>`), `delivery_token_digest` (app-computed SHA-256, because Lua offers no SHA-256 for the `hr1:t` key), `consumer_instance_id` (optional), `record_empty` (`1` records an empty outcome; the long-poll loop passes `0` until its final check so rechecks under the same `operation_id` do not replay an early empty), key prefix `hr1`. Semantics: resolves per-recipient queue/state/message/op/tombstone keys from the ready-index member inside the script — accepted because the first version is standalone Valkey (no Cluster); any future multi-slot deployment must first redesign key declaration. Flow: (1) op record replay — `empty`/`active` replays return the recorded outcome (`replay_empty`; `replay_active` + full recorded response with token and message re-read from the blob); `no_longer_active` → `claim_no_longer_active`; digest mismatch → `operation_conflict`; (2) due or over-limit lease check: `ZCOUNT leases (now +inf)` ≥ max → `limit_exceeded`; (3) scan at most 10 lowest-scored ready candidates; skip-and-continue on: marker present, wrong key types, `status != ready`, head invariant violation, or missing head blob — in that case create the block marker + `blocked` member and remove ready/leases memberships atomically (reported to the caller via a `blocked_detected` count of newly created markers; an existing marker keeps its reason). Two stale derived entries are dropped from `ready` without a marker because authoritative state is consistent: a drained Recipient (no queue, no state) and a `leased` head whose state matches `LINDEX 0`. An unknown `status` value uses `queue_head_mismatch`; (4) claim the first valid candidate: HSET state `{status=leased, delivery_token, claimed_ms, lease_expires_ms=now+duration, consumer_instance_id}`, ZADD `leases` (score `lease_expires_ms`), ZREM `ready`, SET op record `state=active` with token and pointers (TTL 10 min), SET `hr1:t` active phase (TTL 10 min). Returns: `claimed` + `delivery_token`, `message_id`, `delivery_cycle`, `attempt`, `claimed_ms`, `lease_expires_ms`, `message_json`, `blocked_detected` | `replay_active` + same fields | `replay_empty` | `claim_no_longer_active` | `operation_conflict` | `limit_exceeded` | `empty` + `blocked_detected` | `wrong_type`. The long-poll loop is process-side: repeat this atomic script on a 250 ms interval with 0–50 ms uniform jitter until claimed, `empty` at the deadline, or cancellation; the script itself never waits.
- **`ack_v1`** — KEYS: `hr1:t` token record, `ready`, `ready_seq`, `leases`, `blocked` index, stats counter; the queue, head state, block marker, message blob, attempt history, success Hash, and claim op record are resolved inside the script from the token record's pointers (standalone precondition, as for `claim_v1`); the audit Stream is not written by ack. ARGV: `delivery_token`, `token_digest`, `success_ttl_ms`, `tombstone_ttl_ms`, key prefix `hr1`. Preconditions in order: token record absent → `not_found` (unknown token or expired tombstone); terminal `state=acknowledged` → `already_acknowledged` + recorded `message_id`, `acknowledged_ms` (idempotent repeat); marker present → `recipient_blocked` (blocks acknowledgement; no mutation); expected key types. Before any write: the token must match `state.delivery_token` of a `leased` head whose `head_message_id` equals both the token record's `message_id` and `LINDEX 0`, and `lease_expires_ms` must be after Valkey `TIME` (otherwise `stale`; ack is rejected after the actual deadline even before expiry processing). Writes: append nothing to history (M1); SET `hr1:success` (TTL 24 h) from state/blob; DEL message blob and attempt history; LPOP queue; if queue non-empty: re-point state to the new head (`status=ready`, `head_message_id=LINDEX 0`, `delivery_cycle=1`, `attempt=1`, token/lease fields cleared) and ZADD `ready` with `INCR ready_seq`; if empty: DEL state and queue keys and remove the recipient from `ready`/`leases`; DECR stats counter; rewrite token record to terminal phase (`state=acknowledged`, `message_id`, `acknowledged_ms`, TTL 1 h); rewrite claim op record to `state=no_longer_active` (plaintext token deleted). Returns: `acknowledged` + `message_id`, `acknowledged_ms`, `recipient_identity`, `delivery_cycle`, `attempt` (for the feature event and `delivery_attempts_total`) | `already_acknowledged` + `message_id`, `acknowledged_ms` (remaining fields empty) | `not_found` | `stale` | `recipient_blocked` | `wrong_type`. The claim op record keeps its remaining TTL when rewritten to `no_longer_active`; the stats counter never decrements below zero.
- **`block_recipient_v1`** — KEYS: marker, `blocked` index, `ready`, `leases`. ARGV: `recipient_identity`, `reason_code`, `detected_ms`. Idempotent: existing marker with same reason → `already_blocked`; different reason → `already_blocked` + stored reason (never overwritten). Writes: SET marker, ZADD `blocked`, ZREM `ready`/`leases`. Used by reconciliation and claim-time detection.
- **Derived-index repair scripts** (preconditioned, touched only after the caller re-verifies authoritative state): `repair_ready_member_v1` (add/remove one ready membership with fresh sequence, given verified queue/state facts), `repair_lease_member_v1` (add/remove one `leases` membership to match a verified leased state), `restore_dedup_index_member_v1` (ZADD from a verified live record), `remove_stale_dedup_member_v1` (ZREM + DEL for a verified-expired record), `repair_stats_counter_v1` (SET to a verified scanned total). Each returns `repaired` | `precondition_failed` | `wrong_type` and mutates only derived indexes — never authoritative state.
- **Implementation note (ticket 11):** `block_recipient_v1` and the separate derived-index repair scripts are consolidated into `reconcile_recipient_v1` (one Recipient per call: verifies types, the head invariant, head-state completeness, and queued blobs within the per-recipient bound, then either creates the marker + `blocked` member + ready/leases removal atomically with Valkey `TIME` as `detected_ms`, aligns derived memberships, removes stale entries of a drained Recipient, or returns `due_lease` with no mutation), `reconcile_dedup_v1` (batch of digests: expired records deleted with their index member, live records restored into `dedup_age` from `accepted_ms`, orphan members removed), and `reconcile_counter_v1` (compare-and-set of the scanned total, run only on the startup pass). Re-verification and repair therefore happen in the same atomic script; `claim_v1` keeps its inline blocking. A head state without a queue is blocked as `queue_head_mismatch`; a missing or invalid lease field on a leased head as `head_state_missing`.

### Startup reconciliation contract (M1)

Order: configuration validation → Valkey ping and (production) AOF/`noeviction` verification → script load and digest verification → reconciliation → readiness. The administrative listener starts before reconciliation (liveness/readiness/metrics expose startup progress); the public listener opens only after reconciliation succeeds.

- Bounded, batched scans over `hr1:r:*:q`, `hr1:r:*:s`, `hr1:q:*`, `hr1:d:*` (full pass in batches; per-batch bound, never a whole-keyspace `KEYS`).
- Per recipient: queue must be a List, state a Hash (`unsupported_key_type` → block marker); non-empty queue must have state (`head_state_missing` → marker); `state.head_message_id == LINDEX 0` (`queue_head_mismatch` → marker); head and all queued message blobs must exist within the per-recipient bound (`head_message_missing` → marker). Markers are created via `block_recipient_v1`; existing markers are verified against `hr1:blocked` (repair either direction: index members without markers are removed; markers add index members).
- Head state `status=leased`: the `leases` member must exist with score `lease_expires_ms` (repair via `repair_lease_member_v1`); if `lease_expires_ms` ≤ authoritative now, hookrelay performs **no mutation**, emits a critical metric and structured log, and holds readiness false for diagnosis (Milestone 2 replaces this hold with the real expiry transition). `status=ready`: ready member must exist (repair); no `leases` member (repair). Marker present: absent from both (repair).
- Dedup: index members whose record expired are removed with their records; live records missing from `dedup_age` are restored from `accepted_ms`.
- `hr1:stats:queued_messages` is recomputed from scanned queue lengths and repaired when different.
- Repair audit is best effort (XADD when Valkey is available); detection of ambiguity is metered and logged. Repairs touch only derived indexes/counters; authoritative state is never reconstructed. Any inconsistency that cannot be safely isolated or repaired fails readiness; the process is never ready with a detected-but-unhandled inconsistency.
- After readiness, loss of Valkey flips readiness false; recovery re-verifies connectivity, scripting, and (production) persistence settings, and repeats lightweight reconciliation before readiness returns.

### Webhook ingestion (M1 subset)

- Route `POST /webhook/{webhook_type}/{webhook_identifier}`; other methods `405` with `Allow: POST`. Type pattern `[a-z][a-z0-9_-]{0,31}`, identifier pattern `[A-Za-z0-9_-]{1,128}`; slash, encoded slash, colon, whitespace, Unicode, dot segments, and empty values rejected. Unknown type, unknown identifier, and identifier-under-other-type all return the same bounded `404`. Disabled endpoints behave exactly like unknown endpoints (`404`).
- Every response carries a generated UUIDv7 `X-Request-Id`; success bodies are empty; accepted and duplicate produce the same empty `200`; error bodies are empty or platform-minimal (Telegram mapping: unknown endpoint `404`, verification failure `403`, invalid JSON `400`, oversized `413`, blocked recipient / capacity / dependency `503` with `Retry-After: 1`, internal `500`).
- Body: hard limit 256 KiB; declared `Content-Length` above the limit rejected before reading; absent/unacceptable declared length never skips the streaming limit; SHA-256 computed during the read; exact bytes not retained after processing. Media type: `application/json` with optional UTF-8 charset parsed as a media type; others `415`. `Content-Encoding` absent or `identity` only.
- Process protections in M1: a process-local semaphore limits in-flight webhooks to 100 (acquired after route resolution, before body read; excess → `503` + `Retry-After: 1`). Token-bucket rate limiting is configured and validated but enforcement arrives with the Milestone 2 maintenance slice.
- Request context deadline 10 seconds covering body read. `MaxHeaderBytes` 32 KiB, `ReadHeaderTimeout` 5 s, `IdleTimeout` 60 s on the public listener; no global `WriteTimeout` (long polls share nothing with webhooks on this listener, but the setting stays off by design).
- Telegram Verifier: exactly one `X-Telegram-Bot-Api-Secret-Token` header, constant-time compare against the stored credential, no trimming/normalization; optional operator-configured Telegram source CIDR allowlist as defense-in-depth (mismatch → bounded reason `source_ip_denied`); bounded failure reasons `credential_missing`, `credential_repeated`, `credential_mismatch`, `source_ip_denied`.
- Telegram Converter per the adapter design: top-level object with depth ≤ 40 (non-object → `400`); integer-aware decoding (`UseNumber`), `update_id` unquoted nonnegative int64; `source_event_id = platform_deduplication_key = decimal(update_id)`; invalid/missing `update_id` → relay scope, `routing_issue.code = invalid_source_event_id`, fallback dedup key `body_sha256_v1:<base64url>` of exact bytes; event field selection (exactly one known / exactly one unknown / none / multiple) with `platform_event_type` and routing issues per the adapter doc; chat-first Recipient extraction exactly per the event-to-Recipient table; `occurred_ms` from documented per-event date fields (×1000), omitted when absent/invalid; compact re-encoded payload preserving unknown fields and integer precision.
- Deduplication Identity = (Webhook Type, Bot Identity, Platform Deduplication Key); the candidate UUIDv7 `message_id` is generated app-side before `accept_v1` and discarded on duplicate.

### Consumer API (M1 subset)

- Routes on the public listener with shared Consumer Secret Bearer auth (constant-time, uniform `401 unauthenticated`): `POST /v1/deliveries/claim` and `POST /v1/deliveries/ack` only. Request bodies ≤ 16 KiB, depth ≤ 40, unknown fields rejected, `UUIDv7`/integer typing enforced, non-JSON content type `415`; every response carries `X-Request-Id`; optional bounded `Consumer-Instance-Id` header is diagnostic only.
- Claim: `operation_id` mandatory, `wait_ms` optional default 30000 constrained 0–30000; full waiting contract via periodic atomic rechecks (250 ms + 0–50 ms jitter) as specified in `claim_v1`; response/`204`/error statuses and bodies per the Consumer API contract, including `429` with `Retry-After: 1` when active-lease (work-pool-wide, default 100) or waiting-claim (process-local, default 20) limits are exceeded.
- Ack: token-keyed idempotent acknowledgement; success body `{status, message_id, acknowledged_ms}`; repeated identical ack returns the recorded success; outcomes per the `ack_v1` tuple (`404 delivery_token_not_found`, `409 stale_delivery_token`, `409 recipient_blocked`).
- Errors use the bounded Consumer error envelope and allowlist (M1 uses: `invalid_request`, `request_too_large`, `unsupported_media_type`, `unauthenticated`, `operation_conflict`, `claim_no_longer_active`, `consumer_limit_exceeded`, `delivery_token_not_found`, `stale_delivery_token`, `recipient_blocked`, `dependency_unavailable`, `internal_error`).

### Admin API and CLI (M1 subset)

- Admin listener (default `127.0.0.1:8081`) hosts Admin API, health/readiness/accepting-webhooks, `/metrics`, and (best-effort) stdout audit copies. Admin Bearer authentication only — no sessions, no CSRF, no UI in M1.
- `POST /admin/v1/webhooks` and `GET /admin/v1/webhooks/{webhook_type}/{webhook_identifier}` exactly per the Admin API contract: strict 16 KiB/depth-40 body validation, bounded credential-kind allowlist from the Telegram adapter (`secret_token`, 1–256 chars of `A-Za-z0-9_-`), `bot_id` canonical decimal ≤ 20 digits, identifier conflict `409`, bot endpoint limit `409 bot_endpoint_limit_exceeded`, `201` + `Location` + `ETag "<generation_id>:<config_version>"` + safe body (credential kind and `configured: true`, never the value), `404` for missing reads.
- Rejected authentication is audited best effort and never changes the `401`.
- CLI: `hookrelay admin webhook create|get` only. Secret resolution `--admin-secret-file` → `HOOKRELAY_ADMIN_SECRET_FILE` → `HOOKRELAY_ADMIN_SECRET` → hidden prompt on TTY; never a CLI value. Create generates the `wh_…` identifier client-side unless supplied, reports it on uncertain outcomes, and never blindly retries: after a lost response it re-reads the endpoint and reports observed-desired-state with an explicit warning that mutation and audit confirmation remain unproven. Output `table`/`json`; secrets never printed. `generate`, `version`, `healthcheck` per the deployment contract.

### Observability (M1 subset)

- Structured slog JSON to stdout: required envelope fields, `request_id` correlation, feature events `webhook_accepted`, `webhook_duplicate`, `delivery_claimed`, `delivery_acknowledged`, `webhook_endpoint_created`, plus startup/reconciliation and bounded error events (`error_code` + sanitized message). No secrets, tokens, authorization headers, or payloads; body/payload sizes may be logged; empty long polls and health/metrics polling produce no per-request logs.

Capacity gauges (`dedup_oldest_record_age_seconds`, `effective_retention`, `early_evictions`) and maintenance/lease metrics arrive with the Milestone 2 maintenance slice.

The memory-percent stop condition arrives with Milestone 2 maintenance sampling.

### Configuration and lifecycle

- Full `HOOKRELAY_*` flag/env surface per the configuration contract: listeners, `HOOKRELAY_VALKEY_URL` (userinfo redacted everywhere), consumer/admin secrets (file preferred, both-sources error, 16–8192 bytes, entropy documented), `HOOKRELAY_ENVIRONMENT` effects (production requires explicit Valkey URL, nonzero rate limits, AOF + `noeviction`, secure admin cookie; development defaults debug logging), log level, trusted-proxy and Telegram CIDRs, webhook rate/burst/inflight settings, Valkey client limits, queue/dedup/DLQ capacities and retentions, lease/retry policy, maintenance settings, `EXPECTED_PEAK_RATE` with the startup capacity validation `max_dedup_records ≥ expected_peak_rate × dedup_min_retention_seconds`. Settings consumed only by later milestones are validated in M1 but not yet enforced.
- Lifecycle: controlled shutdown deadline 30 s (readiness false → stop ingestion/claims → cancel long polls with `503` + `Retry-After: 1` → drain → stop maintenance → close telemetry; second signal forces; exit codes 0/1/2). Panic recovery at deliberate seams only. A lease created before shutdown is never rolled back.

## Testing Decisions

- A good test asserts external behavior at a seam, never internal structure: HTTP request/response pairs, script status tuples and key states, bounded metrics/log events. No assertion or mocking frameworks; standard `testing`, `t.Helper` helpers, handwritten fakes for caller-owned interfaces, deterministic clock/generator adapters.
- Three layers, matching the agreed seams:
  1. **Composed-application integration (primary seam):** `httptest` servers composed by `app` over a real pinned Valkey via `HOOKRELAY_TEST_VALKEY_URL` (skip locally when absent, obligatory in CI). Covers the full lifecycle: endpoint create/get (including `409`s, credential redaction, `ETag` shape), signed fixture ingestion across all four scopes, duplicate and conflict dedup behavior, claim `wait_ms=0` and waiting contract with recheck timing, ack idempotency and tombstone behavior, claim-replay states, blocked-recipient retryable ingestion and `409` ack, capacity rejections, health/readiness/accepting-webhooks transitions, metrics presence and bounded labels, restart/reconciliation smoke, uniform `404`/`401` behavior, body-limit and media-type handling, and the Telegram adapter table (every event-to-Recipient row, unknown/none/multiple event fields, invalid `update_id`, `occurred_ms` rules) driven through the HTTP seam with signed fixtures.
  2. **Lua transition integration (storage seam):** every script against real Valkey — every status tuple variant, every affected key asserted after success, absence of mutation on every precondition failure, `SCRIPT FLUSH`/`NOSCRIPT` reload path, typed-parser rejection of unknown statuses/shapes, digest-mismatch `operation_conflict`, tombstone phase transitions, TTLs. Reconciliation tests: safe repair of ready/lease/dedup/stats derivations, marker creation on each bounded reason code, refusal of readiness on due leases and unisolatable inconsistencies.
  3. **Unit tests:** pure Telegram Verifier/Converter decisions, Canonical Message codec (absent-vs-null, integer precision via `UseNumber`, compact encoding), config parsing/validation (including production invariants and the peak-rate formula), recipient identity serialization/validation, digest computations.
- Fault tests: ambiguous transport errors after script dispatch are never retried blindly; unknown-script and script-error paths fail the operation and readiness; Valkey-loss flips readiness and recovery re-gates.
- Prior art: none (greenfield); these layers and patterns are prescribed by the code-structure design and are the contract the first tests establish.
- No fake Valkey: it cannot prove script semantics. Testcontainers is not added; the CI service container provides the pinned Valkey.

## Out of Scope

- Negative acknowledgement, lease extension, lease expiry transition, retry policy activation, dead-letter storage/transitions/replay/retention, and the cooperative background maintenance loops that execute them (Milestone 2), including the inline pre-poll maintenance pass, due-lag metrics, and alerting.
- Notification-based long-poll wake-up and its tuning (the periodic recheck contract is complete and compliant).
- Admin CRUD beyond create/get: list, PATCH enable/disable, delete, bot-Webhook listing, cursor pagination; administrative browser sessions, CSRF, login/logout, rate-limited login, `/debug/config`, pprof, and the operational UI.
- Operational/DLQ admin routes (`operations/summary`, `recipient-states`, `recipient-blocks/inspect|clear`, `delivery-state`, `dead-letters…`, `audit` listing) — the storage contracts they need beyond M1's arrive with their slices; the CLI recovery runbook exists only for create (the only M1 mutation).
- Memory-percent acceptance stop (`HOOKRELAY_MEMORY_ACCEPTANCE_STOP_PERCENT` is validated, not sampled) and dedup early-eviction under capacity pressure (both need the maintenance slice; M1 rejects at hard capacity instead).
- Token-bucket webhook rate-limit enforcement (configured and validated in M1); login throttling; distributed quotas.
- Metrics and alerts requiring maintenance loops or history: `oldest_ready_message_age_seconds`, dedup age/retention gauges, maintenance/due-lag series, SLO dashboards; the Compose `observability` profile ships as scaffold only.
- Telegram `setWebhook` automation and Bot API token storage; MaxBot and any second adapter.
- OpenAPI generation, generated clients, backup/restore, `hr2` cutover, periodic consistency checking after startup, multi-process deployment, Cluster-compatible key declaration, arm64 builds, `golangci-lint`.

## Further Notes

- The spike ticket (valkey-go client verification) and the scaffold ticket precede all transition-code tickets; `/to-tickets` should emit the spike first, with a blocking edge to the scaffold.
- Deliberate first-version decisions recorded here because the design left them to this spec: `hr1:t:<digest>` serves as both active-attempt index and terminal tombstone (two phases of one key) so that token-keyed `ack` can locate recipient, message, and claim operation record; `claim_v1` resolves per-recipient keys inside the script from the ready-index member (standalone topology is a precondition); M1 appends no attempt-history entries on the ack path (they are written by M2 nack/expiry and ack deletes history anyway); dedup conflicts return the original `message_id` to the caller for metrics/logs while the public webhook response stays empty.
- Every later milestone extends the same startup reconciliation gate before it may report ready; the due-lease diagnostic hold is explicitly temporary and is replaced by the Milestone 2 expiry transition.
- Operational backup/restore remains deferred by design; Valkey and its artifacts are treated as secret-bearing infrastructure from day one (plaintext webhook credentials and tokens are stored there).
